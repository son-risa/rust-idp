# 要件一覧の決まり

rust-idp の[要件一覧](../../requirements/)（7 覧）は、この頁の決まりで作った。

この頁は、要件 7 覧の定義と決まりを書く。7 覧は、物×処理×権限・画面一覧・設定項目・外部システム・外部の物×処理・データモデル・手順の 7 つの一覧である。中心は物×処理×権限の表で、画面からデータモデルまでの 5 つは、表の操作の id を指して表に結ぶ。手順だけが順番を持つ。手順は目的ごとに、誰が何を順にするかを、ほかの 6 つの行の id を名指して書く。外部の物×処理は、外部システムの 1 行を物と処理に割ったもので、物×処理×権限と同じ形をしている。

どのシステムにも通じる決まりだけを書く。例には、公開の OSS の EC-CUBE（4.3.1）を使う。

この頁で使う語:

- **台本**: 一覧を作り、確かめるスクリプト。
- **約束**: 試験で守ると決めた振る舞い。約束を管理する仕組みを持つシステムだけが使う。
- **赤**: 試験や確かめが落ちること。

## すべての一覧に共通の決まり

1. 一覧の数（行数・本数）は、作る台本が出す。文書や頁に手で書かない。
2. 約束を管理する仕組みを持つシステムでは、約束の文と id を一覧に載せない。約束の文と id はその仕組みの側にだけ置く。一覧には行ごとに約束の印を 1 列だけ置き、台本がその仕組みから付ける。
   - 印は「あり（直）」「あり（親を通して）」「なし」「要らない」の 4 つとする。あり（直）はその行を名指す約束があるもの、あり（親を通して）は結んだ表の操作に約束があるもの、要らないは約束にする中身が無いものとする。物×処理×権限の表では、約束の文の語が当たっただけの結びは数えない。
   - 約束を管理する仕組みを持たないシステムでは、約束の印の列を置かない。
3. 結びの確かさを分ける。コードで鎖を辿れたものは「確か」、名や型から推したものは「見込み」とする。頁では、見込みを点線の札で示す。
4. 想定問答は答えの正本として一覧と別に書かない。一覧の 1 行が答えの正本になり、聞かれ方に合わせた言い換えは LLM がする。外れていないかは試験で測る。
   - 一覧の行 id を引く「試しの問」（人に見せるときの問・試験の問）は、一覧と別の file に置いてよい。問の答えは行 id と根拠の file:行 で書き、行の中身を写さない。問が引く行 id の実在は台本が確かめる。
5. 検算のための数（つながりの数など）は台本の中に持ち、頁には出さない。
6. 約束の印は、試験が操作の入口を呼ぶ約束に加えて、一覧の行の id を名指す要件に結ぶ、今有効な約束からも付ける。外部の物×処理の行も同じ読み方とする。有効でなくなった約束は印から外す。
7. 「十分だと確かめる」決まり（表 20・設定 14・外部 14・データ 15）の道具には、陰性対照として次の 4 つの変異を入れる: 欠け（1 つ消す）・重なり（2 か所に載せる）・範囲の外（持ち主の外の行が引く）・取り違えうる引用（同じ名の file のどちらか決まらない）。変異が入ったことを数えてから走らせる。赤のときは終了コードを 1 にする。
8. 「6 覧」と書くのは、手順を除く 6 つを指すときだけとする。7 つ全体は「7 覧」と書く。
9. 一覧には、元にした版（repo と commit の sha）を持たせる。元が変わって要件化が変わったら、一覧も、一覧から作った写しも作り直す。
10. 1 つの配備の中に分離の単位（組織・テナントなど）を持つシステムでは、「全体」を広さで分けて書く。分離の単位の中のすべてを「<単位>の全体」、単位をまたぐものを「配備の全体」とする。
11. 表の印は本番の構えで判定する。構え（分離の単位の数など）によって値が変わる行やマスは、マスの値を割らず、条件の文にその構えを書く。構えそのものは設定項目の配備の形の行に置く（設定の決まり 20）。

## 物×処理×権限の表

1. 要件は 1 つの表で書く。行（親）は本体の操作 1 つ、その下（子）にその操作を呼ぶ入口を並べる。
2. 親の行は「物と辿り元の組」と「処理」を持つ。辿り元は親・尋ねた人・範囲・全体・直接のどれか。分離の単位を持つシステムでは、全体を「<単位>の全体」と「配備の全体」に分ける（共通の決まり 10）。
3. 処理は、物の何が変わるかで決め、6 パターン（一覧・追加・取得・置換・更新・削除）か残す動詞で書く。
4. 欄を変えるだけで逆の操作で戻せるものは更新、何も変えないものは取得とする。
5. 2 つの物を結ぶもの（中間の物）は独立した行に置き、結ぶ・外すはその行の追加・削除とする。
6. 動詞は、ほかの物を作る・外へ出す・取り消せない・できる人が更新と違う・複数の段の手続き、のどれかに当たるものだけ残す。語は汎用の 9 語と製品で足す語で、元の言い方を下に添える。
7. 1 つしかない物（id を持たない物）は、一覧と追加を「該当しない」とする。
8. 入口は、本体が呼ばれる口の種類で分け（例: API の道・AI の道具・部品の画面・運用の道具（CLI）・内部のきっかけ）、子の行に「呼ぶ先」を書く。画面は、呼ぶ先の操作の下に置く。運用の道具は、配備の運用者が打つ命令を指す。
9. 入口の無い操作には「実装なし（機能の欠け）」か「内部のきっかけで動く（時間・起動・AI の回の中・すべての道にかかる門）」の札を付ける。
10. 権限の列は「誰」と「物との関係」の組。誰と関係は、そのシステムの実際の立場で決め、意味を凡例に書く（例: EC-CUBE の誰はシステム管理者・店舗オーナー・会員・非会員）。
    - 物との関係を持たない誰（内部のきっかけで動く仕組み・配備の運用者など）は、関係で割らない 1 列とする。
    - 代理（なりすまし）中の管理者は「代理される人」として数え、管理者の列に入れない。管理者の列は、管理者が自分として呼ぶときの判定とする。代理で届く道は、その行の条件の文に書く。ある面の身分が別の面の判定を変えるもの（代理・管理者のまま店頭を見るなど）も、同じくその行の条件の文に書く。
11. 人に頼まれて動く誰（AI など）は、頼んだ人の関係を借りるかどうかを書く。
12. 関係は、中間の物と物の欄から決める。表で名指せない関係の列は作らない。
13. マスの値は「可」「断」「条件つき」「該当しない」「口無し」「未確認」のどれかとし、空欄にしない。
    - 「該当しない」はその誰にとって操作に意味が無いとき、「口無し」は意味はあるのに、その誰が呼べる道が無いとき（例: ログインしていない買い物客が自分の注文を見る）とする。決まり 9 の「実装なし」は操作のすべての誰に道が無いとき、「口無し」は一部の誰の列だけに道が無いときに使う。
14. 条件つきは、設定の名か物の欄の値で書く。
15. 断るときは、見えない（一覧に出ない）か、見えるが断るかを分けて書く。
16. 権限は親の行に書く。入口によって違うときだけ、親に「入口で違う」と書き、違う子に値を出す。
17. 後から関係を足せる物（共有・招待・メンバーの追加）は、足す操作の行で、誰が足してよいかを書く。
18. すべての行にかかる門（凍結・許可の一覧など）は、表の外に 1 つ書き、門がかかる行に印を付ける。門がかからない行は名指す。
19. 欠けは、物ごとに OAS（OpenAPI）の 6 パターンと多対多の 9 パターンを当てて洗い、既出・新しい欠け・表の漏れ・当てはまらない、に分ける。
20. 次の 2 つで、表が十分だと確かめる。1 つ目は、本体のすべての入口（API の道・AI の道具など）が子にちょうど 1 回、すべての操作が親にちょうど 1 回載ること。2 つ目は、可と断のそれぞれが本体の認可の処理（file:行）か試験に結ばれていること。死活の確認・外からの受け口・中継だけの道は表の外に一覧する。
21. 約束を管理する仕組みを持つシステムでは、親の行に「約束」の印を置く（共通の決まり 2）。
22. 親の行に「画面から」を置き、その操作を呼ぶ画面・メニューの id を書く。どの画面からも呼ばれない操作は空にする。この欄は画面一覧の「呼ぶ操作」と「行き先」から台本が作り、手で書かない。
23. 子の行に「効く設定」を置く。設定項目で効き先が ①入口 の設定のうち、その道を通すか断るかを変えるものの id を書く。マスの値は、設定が既定のときの値とする。札には、設定の名・効くとき・前→後・確か／見込み・根拠を持たせる。親の行には出さない。
    - 表の印は本番の構えで判定し、そのほかの設定は既定の値とする。
24. 子の行の入口の欄に、その道が呼ぶ外部システムを、外部システムの一覧の id で添える。
25. 権限を決める鍵（URL の前置き・道の名・役など）が業務の単位と違う形の製品では、親の行に「塞ぐ鍵」の列を置き、その行がどの鍵で断になるかを書く。鍵の当て方（前置き・正規表現・完全一致）は表の外に 1 回書く。業務の名と鍵がずれる行（例: 受注の操作なのに出荷の前置きの下にある道）は名指す。
26. 状態の欄の更新で別の物が動くもの（在庫・ポイントなどの副作用）は、更新の行とは別に、誰の列が「仕組み」の行を置く。どの遷移で何が動き、どの遷移で戻るかを遷移ごとに書き、引き起こす操作の行から結ぶ。遷移や副作用が設定 file に書かれているときは、その file:行 を根拠にする。決まり 4 の「逆の操作で戻せる」は、戻すと別の物が動くものには当てない。
27. 拡張の差し込み口（イベントの名・差し替えの口など、外の code が本体に動きを足す所）は入口に数えず、表の外に一覧する。差し込み口ごとに発火する所の file:行 を書き、本体が発火しないものは名指す。差し込み口で足された動きは表の外にあることを、表の頭に書く。

## 画面一覧

表との違い: 表は 2 つの軸（物×処理）で組むので、空いたマスがそのまま欠けの候補になる。画面一覧は 1 つの軸（画面）の木なので、欠けは「どの画面からも呼ばれない操作」と「どこからも辿れない画面」で見つける。

1. 1 行は、画面 1 つかメニューの項目 1 つとする。
2. 行は面ごとに分ける（例: 利用者の画面・管理画面・入口とサインインの画面・チャット・メール・AI の文）。
3. 画面は木で書く。メニューの項目には、並ぶ画面（親）と行き先（決まり 13）を書く。
4. 画面の行には、その画面が呼ぶ本体の操作を表の id で書く。
5. 4 は、表の「部品の画面」の入口から作り、表と画面一覧で同じものを 2 度数えない。
6. 画面が出る条件（役・機能の旗）は、旗の名か物の欄の値で書く。
7. 誰が操作してよいかは画面に写さず、表の権限を引く。
8. 画面は出るのに操作が断られる所と、操作は可なのに画面が無い所を、表と突き合わせて名指す。
9. 本体を呼ばない画面だけの操作は、表の「呼ぶ先 未確認」と対にして書く。
10. 人が使う面の操作は、どれかの画面の行に出る。出ないものは「AI だけ」「API だけ」の理由を書く。
11. すべての画面は、メニューから辿れる。辿れない画面は「リンクで直接開く」と札を付ける。
12. 文言の言葉（訳）は別の決まりに任せ、ここでは書かない。
13. メニューの行には「行き先」を書く。行き先は次の 4 つのどれかとする。
    - 移る: 開く画面の id
    - 操作: 呼ぶ本体の操作の id（表の親）
    - 画面の中だけ: 本体に要求を出さず、画面の中で開く・写す・手元に保存するだけ
    - 表に無い: 押すと本体が動くのに、表にその操作の行が無い。何が起きるかを 1 文で書き、根拠の file:行 を添える
14. 木は 3 段とする。1 段目は面の入口（一番外側の枠）、2 段目は画面とメニュー、3 段目はメニューだけとする。3 段目に画面は置かない。
15. メニューの項目は、押すと画面が移るか、本体の操作が動くか、画面の中が変わる所とする。左のナビだけでなく、右クリックの項目・カードのボタン・絞りのタブも含める。画面の中のボタンの多くはメニューの行にせず、画面の行の「呼ぶ操作」に載せる。
16. 行き先が「表に無い」のメニューは、表に行を足すか、表の外に置く理由を書くかを決めるまで残す。

## 設定項目の一覧

表との違い: 表は 2 つの軸（物×処理）で組むので、空いたマスがそのまま欠けの候補になる。設定項目の一覧は 1 つの軸（設定）の並びである。置き場・範囲・誰が変えるかは、行ごとにほぼ 1 つに決まる（環境なら配備全体と運用者、管理画面の設定なら組織の管理者）。そのため、欠けは「変える口が無い設定」と「優先を名指せない重なり」で見つける。

1. 1 行は、設定 1 つ（環境変数 1 つ・設定 file の欄 1 つ・DB の設定 1 つ）とする。
2. 行は、名・置き場・種類・効く範囲・誰が変えるか・変える口・既定・読む所・効き目の欄を持つ。加えて、効き先（決まり 15）・効く所（決まり 16・17）・外部（決まり 19）・親の欄を持つ。約束を管理する仕組みを持つシステムでは、約束の欄（共通の決まり 2）も持つ。
3. 置き場は環境・設定 file・DB のどれかとし、DB の設定にはどこから来たか（管理画面の設定・機能の旗・本人の設定・表の物など）を添える。
4. 効く範囲は配備全体・組織・範囲・個人のどれかとし、範囲のときは組織の値との合わせ方（下限・上限・上書き・どちらかが on）を書く。
5. 誰が変えるかは運用者・組織の管理者・本人・変えられないのどれかとし、DB の設定は表の権限（変える操作の親の行）から引く。
6. 変える口は管理画面・利用者の画面・API の道を表の親の id で書き、口の無い設定には「無し（env を直して立て直す）」のように直し方を書く。
7. 既定は読み口の行に書かれた値を書き、行に無いときは「読み口の行に無し」と書く。
8. 読む所は今の木の file:行 を書き、別の木から借りた行は使わない。
9. 効き目は何が変わるかを 1 文で書き、秘密の値は書かない。
10. 同じ意味の設定が 2 つ以上の置き場に在るものは重なりとして 1 組にまとめ、優先の順（DB が勝つ・環境が勝つ・両方要る・並んで効く）と根拠の file:行 を書く。
11. 設定 file の欄から別の道具が環境変数を作るものは重なりに入れ、優先を「設定 file から作る」と書く。
12. 同じ置き場に 2 つ以上の道で書くものは、重なりと分けて名指す。
13. 名を実行時に決める読み口と、開けない場所の読み口は「読めなかったもの」に一覧する。
14. 次の 2 つで、一覧が十分だと確かめる。1 つ目は、そのシステムの設定のすべての読み口（環境変数・設定 file の欄・DB の設定）が一覧にちょうど 1 回載ること。2 つ目は、変える口に書いた親の id がすべて表に在ること。
15. 「効き先」は次の 4 つのどれか 1 つとし、確か／見込みを添える。
    - ①入口: 表の道を通すか断るかを変える
    - ②結果: 道は通したまま、動いた結果（大きさ・待ち時間・中身など）を変える
    - ③つなぎ先: 外部システムの宛先・鍵・資格情報
    - ④土台: 本体を動かす土台（URL の道・中継先・起動の仕方など）
    - ①入口 と書く前に、道の側（本体の判定）で効くかを読み口で確かめる。画面の部品を出し入れするだけで道は開いたままの設定は、①入口 にせず「見た目だけ」の札を付け、開いたままの道の id を「効く所」に書く。
16. ①入口の設定は、「効く所」に、絞る表の道（子の行）の id と、効くとき・前→後・根拠を書く。表の側には、同じ結びを「効く設定」として出す（表の決まり 23）。どの道も絞らない ①入口 の設定には、絞らない理由を書く。
17. ②結果の設定は、「効く所」に効く所を 1 文で書く。③と④は「効く所」を空にする。③は外部システムの一覧の「有効にする設定」で結ぶ。
18. 約束を管理する仕組みを持つシステムでは、設定の約束を 1 行に 1 本ずつ書かない。欄（既定・効き目・優先・誰が変えるか）ごとに、全行をなめる約束で覆う。その約束は、1 行の既定を変える変異や、優先を逆にする変異で赤になることを確かめる。
19. 「外部」の欄には、その設定が効く外部システムを、外部システムの一覧の id で書く。
20. 「配備の形」（OS・言語と枠組みの版・動かし方・台の数）を設定の行に置く。脆弱性が当たるかは道でなくこの行で決まることがあるので、要件として答えられるようにする。置き場は「配備」（決まり 3 の環境・設定 file・DB に足す 4 つ目で、この行だけに使う）、効き先は ④土台 とする。配備の手順（migration・カナリア・リリースの進め方）は、この行にせず要件の木の枝に置く（「一覧の外に置くもの」の 1 つ目）。

## 外部システムの一覧

表との違い: 表は本体の操作を行にする。外部システムの一覧は外の相手を行にし、表の親の id を指して結ぶ。系統×システムの表にすると名の重なりが多く、マスの多くが「－」になるので、システム 1 つを 1 行にする。

1. 1 行は外部システム 1 つとし、系統（AI の提供元・本人の連携・受け口など）は行の中の「用途」に書く。
2. システムは、鍵と設定の束を別に持つ相手のサービスで分け、同じ会社でも束が違えば別の行とする。
3. 種別は「外部の相手」か「基盤」とし、本体の記録・配備・計測などを支えるものを基盤とする。
4. 向きは「出る」「受ける」「両方」のどれかとし、受けるものには確かめ方（署名）を書く。
5. 認証の形は OAuth・鍵・署名・なしから選び、用途で違うときは並べて書く。
6. 誰の権限で呼ぶかは、組織（会社の鍵）・本人（本人の接続）・配備（環境の鍵）のどれかで書く。どこの費用・利用枠・記録に付くかは、この欄で決まる。
7. 有効にする設定は設定の名で書き、設定の節と同じ名を使う。
8. 呼ぶ本体の操作は表の親の id で書き、すべての操作が通るもの（DB・誤りの報告など）は「すべての親（横断）」とする。
9. 中継の道は本体から外へ出る所を file:行で書き、本体の外（開発の道具・配りの scripts など）だけにある出口は「本体の外」として別に名指す。
10. 止まったときの見え方は「断」「待つ」「黙って落ちる」で書き、黙って落ちるものには握りつぶす所（file:行）を添える。
11. 本体の中から外への通信を絞る門があるときは、表の外の門（表の決まり 18）として 1 つ書き、システムの行には置かない。
12. 宛先が設定や引数で決まる出口は、宛先を決める設定の名と一緒にどれかの行に載せ、載せられないものは「結べない」と名指す。
13. 外と話さない依存（画面の部品・構文の部品など）は一覧に載せず、部品の一覧に分ける。
14. 次の 3 つで、一覧が十分だと確かめる。1 つ目は、本体の外向きの口がすべて、システムの行・部品・本体の外のどれかにちょうど 1 回載ること。2 つ目は、宛先が値の出口を全数で当てること。3 つ目は、結んだ親の id がすべて表に在ること。

## 外部の物×処理の一覧

外部システムの一覧は、システム 1 つを 1 行にしている。そのため、本体が外部の何を読み・作り・消すかと、それを誰の権限で行うかまでは書けない。この表は外部システムの一覧を 1 段細かくし、外部システムがどう働くかを聞かれたときの答えの正本にする。答えるのは本体が外部に何をするかで、外部のサービスの中の動きは扱わない。

1. 1 行は、外部の物 1 つ（メールのメッセージ・カレンダーの予定・チャットのメッセージ・issue など）× 処理 1 つ（一覧・取得・追加・更新・削除・送る・受けるなど）とする。
2. 行は、外部システム（外部システムの一覧の id）・外部の物・処理・呼ぶ道具・本体の関門・外部の関門・持ち込み先・確か／見込みの欄を持つ。
3. 呼ぶ道具は、本体の側の入口（AI の道具名・API の道・cron・webhook の受け口）を file:行 で書く。
4. 本体の関門は、その呼び出しを許す・止める判定（権限・設定・役）を書き、表の親の id に結ぶ。
5. 外部の関門は、誰のトークンで呼ぶか（組織の鍵・本人の OAuth・仕組み）・求める scope・外部側で要る権限を書く。
6. 持ち込み先は、結果が入る本体の物と、そこでの共有の範囲（本人だけ・参加者・組織など）を書く。入らないものは「入らない」と書く。
7. 道具が実行時に決まる相手（MCP サーバなど）は、物を並べられないので 1 行にし、本体の関門と外部の関門だけを書く。
8. 確かめの対象にするのは、本体の関門・誰のトークンか・持ち込み先と共有の範囲とする。約束を管理する仕組みを持つシステムでは、この 3 つを約束にする。外部の関門の scope と外部側の権限は、外部を呼ばないと確かめられないので、説明として載せて「見込み」の印を付ける。
9. 範囲は外部の相手（外部システムの一覧の種別が「外部の相手」の行）とし、基盤は後に回す。
10. 外部システムの一覧の各行から、その相手の行だけに絞った外部の物×処理へ移れるようにし、外部の物×処理の行からは外部システムのその行へ戻れるようにする。

## データモデルの一覧

ほかの一覧との違い: ほかの一覧は本体が何をするかを行にする。データモデルは本体が何を記録するかを、DB の表 1 つを 1 行にして書く。行の中身はデータモデルの記法（決まり 5〜12 で決める書き方）で書く。頁では表の欄に割り、元の記法の行は行ごとに開いて読めるようにする。

1. 1 行は DB の表 1 つとする。本番の木の DB の目録から台本で書き起こし、手で行を足さない。
   - 行の id は D-001 の形の連番とする。表の名と番号の対応は 1 つの file で固定する。表が増えたら次の番号を足し、消えた表の番号は使い回さない。ほかの一覧からはこの id で指す。記法の行は表の名のままとする。
2. 表の種類は、そのシステムの DB の形で決める（例: 列を持つ表・鍵と JSON の値だけを持つ表・DB に表が無いが id が指す相手の「外の物」）。
3. 表の名は DB の表の名のまま（英語・複数形のまま）とする。日本語名を付けるときは、単数と複数を言い分けない簡単な語にする（「会話たち」でなく「会話」）。
4. 日本語名を付けていない表は、`?{表の名}` の印で「名が無い」と示す。名が無い表の数は台本が出す。
5. 表どうしの関係は 3 つの記号で書く。`--` は親が消えると一緒に消える（DB の CASCADE）、`->` は指している間は相手を消せない、`~>` は指すが DB は縛らない。
6. 関係の確かさを分ける。DB に外部キーがあるものは「宣言」、外部キーは無いがコードが id を突き合わせているのを確かめたものは「コード」（`<logical code>`）とする。名や型から推しただけのもの（`<logical guess>`）は載せない。
7. id を持つが関係にしない列は、理由を 1 行添えて「関係にしない列」として名指す（2 種の値が混ざる列・書く所が無い列など）。黙って落とさない。
8. 相手の表が決まらない id（値によって、外の物のどれかを指す列）は `{a|b via 列}` で相手を並べる。
9. 整数で持つ日時（ミリ秒）は `datetime(ms)` と書き、JSON の中の鍵も同じにする。
10. JSON の中の鍵からの参照は `via 列.鍵`、主キーでない列の組を指す参照は `via (..) to (..)` で書く。`to` の組は、参照先の `@unique` のどれかと同じか、参照先の主キーを全部含む組にする。
11. 索引の名前・降順・方法・CHECK の名前・記法に無い型・表の設定などの物理の性質は、論理の行と分けて末尾の `@pg` の行に書く。頁では「物理」の欄に数だけ出す。
12. 記法で書けない物（読んでいない JSON の鍵・型の別名・extends・次元の無い vector など）は、表の行に「書けない物」として残し、種類ごとの数は台本が出す。
13. 物×処理×権限の親の行に「記録する表」の列を置き、その操作が入口から辿って読む・書く表を D の id の札で並べる。データモデルの行には逆向きの「使う操作」の列を置く。入口から表に触る関数まで、helper を 2 段まで挟んで file:行 で辿れたものを確か（実線）、名前が合うだけのものを見込み（点線）とする。共通の前置き（認可の配線など）だけで届くものと、失敗の時だけ通る道は、札にせず数だけ出す。
14. 監査・誤りの記録・認可の名簿・版の確かめのように多くの操作が通る表は「横断」とし、本表の札には出さない。どの操作にも結ばない表は、「内部の仕組み」「非同期の境の先」「辿り切れなかった」のどれかの理由を付けて名指す。辿り切れなかったものと内部の仕組みは混ぜない。
15. 次の 3 つで、一覧が十分だと確かめる。1 つ目は、目録の表がすべてちょうど 1 行になること。2 つ目は、関係の相手がすべて行に在ること。3 つ目は、`@pg` の行がすべてどれかの表に結べること。
16. DB の表のほかに、DB の外に持つ業務の物（画面から書き換える雛形の file・画面が書く .env・上げた file など）を「DB の外の持ち物」として行にし、置き場と、書く操作の id を書く。移行やバックアップの範囲を行で答えるためである。決まり 1 の「手で行を足さない」は DB の表の行にだけ当てる。

## 手順の一覧

ほかの一覧との違い: ほかの 6 つは部品（誰がどの操作をできるか・どの画面と設定があるか）を持つが、段の順と、本体の外（外の提供元）の準備は持たない。手順は「〜できるようにするには、誰に何を頼み、自分は何を順にするか」の問いに答える正本で、段ごとに 6 覧の行を名指す。

1. 1 行は目的 1 つとし、id は T-00 の形の連番とする。目的の下に段を並べ、段の id は T-01-1 の形とする。1 つの段が提供元ごとに分かれるときは T-01-1a〜1d の枝にする。
2. 目的は、ほかの目的を前提にするときに「前提」の欄でその id を名指す。T-00 は、どの手順も前提にする配備の土台（運用者が触る、多くの操作に効く設定）とする。
3. 段は、段の種類・誰が・関わり・提供元・すること・確かめ・6 覧の行の欄を持つ。
4. 段の種類は「外部の準備」「配備の設定」「組織の設定」「本人の準備」「物×処理」の 5 つのどれかとする。
5. 誰がは、物×処理×権限の権限の列の誰から選ぶ。配備の運用者のように物との関係を持たない誰も、表の決まり 10 の関係で割らない 1 列を持つ。
6. 関わりは、物との関係を名指したいときだけ書く。書かないときは、その誰がのどれかの関係で許されていればよい。
7. 確かめは「本番で通した」「画面の案内文から」「無し」「AI の選び次第」のどれかとする。本番で通した段は、確かめた日と提供元を目的の行に書く。「AI の選び次第」は、AI がその回にどの道具を選ぶかで段が変わるものに付ける。
8. 6 覧の行の欄には、段が触る操作（A-）・画面・設定・外部システム（X-）・外部の物×処理・データモデル（D-）の id を書く。提供元の画面の項目の名は、提供元の画面のとおりに写す。
9. 台本が頁を作るときに、手順を 6 覧に照らす。次のどれかに当たると、頁を作らずに止める。
   - 名指した id が 6 覧に無い
   - 名指した操作が、段の「誰が」（関わりを書いたらその列）で可でも条件つきでもない
   - 関係で割らない誰（配備の運用者・仕組みなど）の段が、その誰の変える設定でない設定を名指す
   - 前提に書いた目的が無い、段の id が 2 度出る、種類・誰が・関わり・確かめが決めた語でない
10. 手順は約束にしない。手順が古くなったことは、9 の照らしで止めて知らせる。
11. 約束を管理する仕組みを持つシステムでは、手順が名指す操作のうち、約束の印が「なし」「未確認」のものを、約束にする順の先頭に置く。
12. 答えるときは、書いてある目的の手順だけを答える。書いていない目的は「この一覧には手順を書いていない」と答え、6 覧の部品から順を推して組み立てない。書いてある目的の中でも、書いていないとした段は 6 覧で埋めない。
13. 目的の候補は、物×処理×権限で書く操作を持つ物から挙げ、順に足す。
14. 手順のデータは 1 つの file に置き、台本が頁の手順のタブを作る。写しを作るときは、その file から作る。

## マスターを持つシステムでの作り方

EC-CUBE 4.3.1 のコードで確かめた作り方である。

- マスターとは、管理者が営業の前に登録し、利用者の道を変える表のこと（商品・配送方法・支払方法・宿・部屋タイプ・プランなど）。店や予約のシステムには有る。
- データモデルの覧で、マスターの表に印を付ける。
- マスターの表ごとに「型の欄」を挙げる。型の欄とは、コードの分岐（検査・画面の出し分け・振り分け）が読んでいる欄のこと。たとえば EC-CUBE の商品では、規格の数・在庫を数えない・販売の上限数・販売種別が型の欄になる。値そのもの（個々の商品）は挙げない。
- 型どうしの鎖を書く。EC-CUBE では、販売種別が配送方法を絞り、配送方法が支払方法を絞る。途中で 0 件になると買えない。
- 升の軸は「店の摘み × マスターの型」の 2 つにする。行に並べるのは、型の組み合わせのうち道が変わるものだけ。鎖の上で 0 件になる組み合わせも含める。
- 質問の例も、マスターの型ごとに作る。
- 権限の段は、管理者と一般を基本にする。管理者が運営者と、拠点ごとの管理者（予約のシステムなら宿ごと）に分かれることがある。一般も会員とゲストに分かれることがある。「自分の拠点」「自分の予約」は、物×処理×権限の表の関わりの列で書く。
- 外部システムが要件の大きな部分を占めるとき（予約のシステムの OTA など）は、覧を作る前に聞き取る。聞くのは、相手の数と名前、直接かサイトコントローラ経由か、物ごとにどちらを正にするか、知らせの届き方、二重予約の扱い、仕様書・試しの環境・契約の有無。答えで外部の 2 つの覧の行数と見積もりが大きく変わる。

## 一覧の外に置くもの

- 運用と配備の手順（migration・カナリア・リリースの進め方など）は、新しい一覧にしない。要件の木（要件を枝分かれで並べた文書）に 1 本の枝として足し、shell の検査をそこへ結ぶ。ただし、動いている配備の形（OS・版・動かし方・台の数）は、設定項目の決まり 20 で設定の行にする。枝に置くのは配備の手順、行にするのは配備の形と分ける。
- すべての一覧にまたがる横の決まりは、新しい一覧にせず、横の決まりとして別に持つ。
