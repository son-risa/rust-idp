# ユースケース

この頁は 2 部に分かれています。1 部は、rust-idp がいまできることです。2 部は、まだできない AI エージェントのユースケースと、それに要る仕様です。

仕様を実装したら、その行を 2 部から 1 部へ移します。仕様を足す pull request では、この頁も直します。

## 1 部　いまのユースケース {#today}

| ユースケース | 何が起きるか | 使う仕様 |
|---|---|---|
| 業務アプリにパスキーでログインする | 利用者が、合言葉なしで Web アプリにログインする（本番では、マルチテナントの業務アプリ AMATE） | OpenID Connect の認可コードフロー、PKCE、WebAuthn（パスキー） |
| 招待で参加する | アプリが rust-idp に登録のリンクを頼み、自分のメールで送る。招かれた人は、リンクからパスキーを登録する | confidential client の認証（`client_secret_basic` または `private_key_jwt`） |
| 危ない操作の前に、別の端末で承認する | アプリが、ある 1 つの操作について承認を求める。利用者は自分の端末のパスキーで承認する。何を承認したかが、そのまま記録に残る | CIBA（poll モード）、Rich Authorization Requests（RAR） |
| 価値の高い API を守る | client は、ログイン・要求の開始・API の呼び出しのたびに、自分の鍵を持っていることを示す。トークンを盗んだだけでは使えない | `private_key_jwt`、Pushed Authorization Requests（PAR）、PKCE、DPoP |
| 管理者の決めた強さで client を登録する | client を、決まった手順（プロトコル）で登録する。どこまで厳しくするかは管理者が決め、client の側からは弱められない | Dynamic Client Registration（RFC 7591） |

それぞれについて、何を形式検証しているかは[検証](verification.md)の頁にあります。かいつまむと次のとおりです。

- パスキーのログインと PKCE、DPoP、`private_key_jwt`、CIBA と RAR には、Tamarin のモデルがあります。
- PAR には、モデルがありません。
- どれも認証（certification）は受けていません。

## 2 部　AI エージェントのユースケース（これから） {#agents}

AI エージェントが、人や組織の代わりに読む・頼む・注文する・支払う場面が増えています。そうなると、IdP は次の 3 つの問いに答える必要があります。どれも、合言葉や共有の秘密では、うまく答えられない問いです。

- **これはどのエージェントか。** 「鍵を持っている誰か」ではなく、どのソフトウェアの、どの実体か。
- **誰の代わりに動いているか。** 責任を負う人や組織を、トークンに記録する。
- **何を、いつまでしてよいか。** 利用者の権限をまるごと渡すのではなく、狭く、短い権限にする。

下の例は、それぞれの仕様が何のためにあるかを示すために書いたものです。実在の製品を説明したものではありません。

### 組織と組織

| ユースケース | 何が起きるか | 守るべきこと | 使う仕様 |
|---|---|---|---|
| 見積もりの依頼 | 小売のプロジェクトが、製造 2 社のエージェントを招く。各社のエージェントは依頼を自社に持ち帰り、自社の社員と見積もりを作って、期限までに返す | 小売は、製造各社のエージェントを自社の利用者として登録しない。代わりに各社の IdP を信頼し、このプロジェクトに限ったトークンを渡す | Identity Chaining、Token Exchange（`act`）、RAR、DPoP |
| 在庫の自動補充 | 店のエージェントが問屋の在庫を確かめ、決めた額までは自動で発注する | 上限を超える発注には、人の承認が要る | RAR、CIBA |
| 監査の資料の受け渡し | 会計事務所のエージェントが、顧客の会計システムから決算の資料を集める | 決めた資料だけを、監査の期間だけ読ませる。どの事務所の誰の代理かを記録に残す | Resource Indicators、RAR、Token Exchange（`act`） |
| 共同研究のデータの共有 | 大学と企業のエージェントが、互いの実験データを取り合う | どちらも、相手の組織の人を自分の名簿に載せない | Identity Chaining |
| 障害の連絡 | クラウドの事業者のエージェントが、顧客の運用のエージェントに障害を知らせ、顧客の側の状態を読んで原因を切り分ける | 夜中に人がいない所で動くので、どの実体かを確かめる。トークンを盗まれても使えないようにする | WIMSE のワークロードの身元、DPoP |

### 個人と組織

| ユースケース | 何が起きるか | 守るべきこと | 使う仕様 |
|---|---|---|---|
| 旅行の手配 | 個人のエージェントが、航空会社とホテルのサイトを訪ね、空きを調べて予約する | 調べるだけならログインは要らない。予約と支払いにはログインが要り、支払いには本人の承認が要る | Poppy（Personal Agent Protocol）、CIMD、CIBA |
| 役所の手続き | 個人のエージェントが、住所の変更と、それに伴う電気やガスの手続きを出す | 役所が、エージェントが本人の代理だと確かめられる | Token Exchange（`act`）、`private_key_jwt` |
| カスタマーサポート | 個人のエージェントが、通信会社のサポートのエージェントと話し、明細を確かめてプランを変える | 本人は、合言葉をエージェントに渡さない | CIMD、Token Exchange |
| 病院の予約 | 個人のエージェントが病院を予約し、前の病院の検査結果を新しい病院に渡す | 検査結果は、その病院のその受診にだけ見せる | RAR、Resource Indicators |
| 社員が、自分のエージェントで仕事をする | 社員のアシスタントのエージェントが、社内の勤怠や経費のシステムを使う | 会社の IdP が、社員本人の session ではなく、社員のエージェント用のトークンを出す | ID-JAG、Token Exchange |

### 個人と個人

| ユースケース | 何が起きるか | 守るべきこと | 使う仕様 |
|---|---|---|---|
| 日程の調整 | 2 人のエージェントが空いている時間を見せ合い、会議を決める | 空きだけを見せ、予定の中身は見せない | RAR |
| 割り勘 | 幹事のエージェントが、参加者のエージェントに精算を頼む | 決めた額を超える送金は、払う本人の承認なしには行わない | RAR、CIBA |
| フリマの売り買い | 買い手のエージェントが、売り手のエージェントと値段を交渉する | 買い手が、そのエージェントが本当にその売り手のものかを確かめられる | CIMD、Token Exchange（`act`） |
| 家族の見守り | 親のエージェントが、子どもの位置や帰宅の知らせを受け取る | 何をいつまで見せるかは、子どもの側で決める | RAR、CIBA |

### 仕様と rust-idp での状態 {#specs}

状態の見方:

- **対応済み**：いま実装されている。
- **計画中**：次に足すつもり。
- **検討中**：上のユースケースの広がり次第。
- **様子見**：いまは足す予定がない。

成熟度の見方:

- **確定標準**：RFC、または OpenID の Final 仕様。
- **WG 採用ドラフト**：IETF の作業部会（WG）が採用したもの。まだ変わりうる。
- **個人ドラフト**：作者による提案。
- **業界仕様**：標準化の団体の外で公開されたもの。

| 軸 | 仕様 | 何をするか | 成熟度 | rust-idp |
|---|---|---|---|---|
| エージェントの身元 | `private_key_jwt`（RFC 7523） | client が自分の鍵で名乗る | 確定標準 | 対応済み |
| エージェントの身元 | Dynamic Client Registration（RFC 7591） | 決まった手順で client を登録する | 確定標準 | 対応済み |
| エージェントの身元 | Client ID Metadata Document（CIMD） | client_id を URL にし、サーバがそこから client の情報を取りに行く | WG 採用ドラフト | 計画中 |
| エージェントの身元 | OAuth Client Attestation | client が、そのソフトウェアの本物の実体であることを示す | WG 採用ドラフト | 検討中 |
| 委譲 | CIBA | 別の端末で、人に承認を求める | 確定標準 | 対応済み |
| 委譲 | Rich Authorization Requests（RFC 9396） | 額・期間・品目など、細かい条件を認可に書き込む | 確定標準 | 対応済み |
| 委譲 | DPoP（RFC 9449） | トークンを鍵に縛り、盗んだトークンだけでは使えなくする | 確定標準 | 対応済み |
| 委譲 | Token Exchange（RFC 8693） | トークンを狭いものに交換する。`act` で、誰が誰の代わりに動くかを記録する | 確定標準 | 計画中 |
| 委譲 | Identity Chaining | 組織をまたいで、身元と認可を引き継ぐ | WG 採用ドラフト | 検討中 |
| 委譲 | Identity Assertion JWT Authorization Grant（ID-JAG） | 組織の IdP が利用者を保証し、別のアプリがトークンを出せるようにする | WG 採用ドラフト | 検討中 |
| 委譲 | Transaction Tokens | 社内のサービスの間で、呼び出し元の文脈を持ち回る | WG 採用ドラフト | 様子見 |
| 宛先と発見 | Resource Indicators（RFC 8707） | トークンの宛先を 1 つのサービスに縛る | 確定標準 | 一部対応。点検を計画中 |
| 宛先と発見 | Authorization Server Metadata（RFC 8414） | OAuth の client 向けに、サーバの情報を公開する | 確定標準 | 計画中（OpenID Connect の discovery は対応済み） |
| 宛先と発見 | Protected Resource Metadata（RFC 9728） | リソースサーバが、使うべき認可サーバを client に知らせる | 確定標準 | 対象外（リソースサーバの側の仕様） |
| 判断 | AuthZEN Authorization API 1.0 | 外の判断エンジンに、認可の判断を問い合わせる | 確定標準 | 様子見 |
| 組み合わせ | WIMSE AI agent identity（AIMS） | ワークロードの身元と OAuth を、エージェント向けにどう組み合わせるか | WG 採用ドラフト | 様子見 |
| 組み合わせ | PACT（draft-valverde-oauth-pact） | CIBA・Token Exchange・client attestation で、エージェントに委譲する | 個人ドラフト | 様子見 |
| 組み合わせ | Poppy（Personal Agent Protocol） | 個人のエージェントのための正面玄関。まずゲストとして見せ、要るときだけログインと狭い権限を求める | 業界仕様 | 様子見（`private_key_jwt` と DPoP は対応済み。CIMD は計画中） |

ドラフトの仕様は、公開されるまでに変わることがあります。rust-idp がドラフトを実装したときは、この頁に版を書きます。
